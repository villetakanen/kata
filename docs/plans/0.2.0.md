# Kata 0.2.0 plan

Redesigned direction, 12 October 2026. Status: complete, 12 October 2026.

## Goal

Help people and agents choose a visual form for the audience's question, explain
the trade-offs, and recognize when the familiar forms do not fit. Add the
golden cut as an optional compositional pattern and evaluate whether Kata's
guidance helps agents produce faithful, readable Lys slides. The evaluation
must be repeatable with Claude Code, Codex CLI, and pi when those tools and
their model access are available.

0.2.0 remains a slide-focused release. It strengthens the current repertoire;
it does not claim that the golden ratio improves beauty, comprehension, or
attention, and it does not expand into general deck storytelling.

## 1. Make pattern choice explicit

Revise the delivered skill into a short decision framework that works for a
person choosing a form and an agent explaining its choice:

1. State the audience's question and the decision or understanding it supports.
2. Identify the information's actual relationship: alternatives on shared
   criteria, parts of a known whole, nested membership, dependencies, change
   over time, or one primary idea balanced with supporting context.
3. Check whether the data supports that relationship and whether the medium,
   density, and reading context allow it to remain legible.
4. Choose the matching pattern, adapt it, separate questions, or name a better
   representation outside Kata's catalogue.
5. Explain the consequential trade-off and preserve values, units, scope,
   uncertainty, and caveats.
6. Review the rendered result for fidelity, grouping, label association,
   emphasis, reading order, and legibility.

The framework must allow "none of these" and say what information would change
the choice. It should be concise enough to follow in a live task, while the
pattern references hold examples and details. Do not turn the checklist into an
automatic scoring system or imply that one pattern wins independent of purpose.

## 2. Add the golden-cut pattern

Add a reference for an asymmetric composition: one primary message or visual
field receives more space, with a secondary field for context, evidence, or
qualification. Explain the conventional 61.8/38.2 division as an optional
starting proportion, not a target to force onto every canvas. Cover useful
cases, poor-fit cases, adaptation, and at least one worked Lys example.

The decision framework must distinguish this composition from the existing
data-relationship patterns. A golden cut can organize emphasis around an
already-understood message; it cannot establish that a quantity is 61.8% of a
whole, make unequal categories comparable, or justify a winner. Keep actual
data values encoded proportionally and labels attached to their evidence.
Describe phi grids or recursive subdivisions only where they clarify the
example; typography, spacing, and a golden rectangle canvas are not required.

Show a case where the asymmetric emphasis helps and one where it gets in the
way, such as competing claims of equal importance or a dense comparison needing
shared alignment. Let purpose and evidence decide which field is primary.

## 3. Evaluate the guidance through Lys

Build a small, versioned set of unfamiliar briefs with source facts, an
audience question, constraints, and an answer key for data fidelity. Include
both positive and negative cases: cases suited to the golden cut, cases suited
to another Kata pattern, and cases that should trigger an explicit mismatch or
request for missing information. Include at least one untidy brief with
missing values, mixed units, overlap, or uncertainty.

Run each brief in these conditions when practical:

- Plain Lys authoring instructions, without Kata.
- The installed 0.1.0 Kata skill with Lys.
- The 0.2.0 candidate skill with Lys.

Hold each CLI, model, model settings, task wording, source material, output
requirements, and brand constant across conditions. Record tool and version,
model identifier, settings, date, prompt, skill revision, exit status, and
artifacts. A missing CLI or failed run is reported as unavailable or failed,
not silently excluded. Do not combine results across models and describe them
as one head-to-head tool comparison.

### Runner requirements

- Provide a common task manifest and a CLI adapter interface that passes the
  same prompt and source files to each supported tool and captures its final
  response, metadata, exit status, and run log.
- Ship adapters for Claude Code (`claude -p`), Codex (`codex exec`), and pi
  (`pi -p`). Keep executable paths and model/settings arguments configurable;
  never put credentials in manifests or checked-in artifacts.
- Keep generated work in per-run directories. Require a Lys-compatible HTML
  deliverable and an accompanying rationale or decision record. Validate the
  output structurally and render it with Lys for visual and reading checks.
- Make the same evaluation runnable for one selected CLI or for all configured
  CLIs. Document prerequisites and a short local invocation; API access or a
  signed-in CLI is supplied by the evaluator.
- Store outputs and results in a clearly separated, reproducible results
  location. Do not overwrite source examples or the live Kata skill during an
  evaluation.

### Evaluation criteria

Score or record separately:

- **Choice quality:** Does the form answer the audience's question? Does the
  agent select a non-golden pattern or reject the catalogue when appropriate?
- **Data fidelity:** Are all relevant facts, units, denominators, missingness,
  uncertainty, and caveats preserved? Are encodings proportional?
- **Reasoning:** Is the consequential trade-off explained without unsupported
  aesthetic, psychological, causal, or decision claims?
- **Lys artifact:** Does it render, remain readable at presentation and phone
  sizes, work with keyboard navigation, expose useful content without
  JavaScript, and print without clipping?
- **Reader task:** Can a reviewer answer the brief's stated audience question
  from the artifact? Record human reader outcomes separately from agent
  self-review and automated checks.

Use blind artifact IDs for human review where feasible. Record failures, ties,
and uncertainty as well as improvements. Report completion counts and the
limits of the sample; attractive specimens or automated structural checks do
not establish improved comprehension. Use evaluation findings to revise the
decision framework and examples.

## 4. Research and claim boundaries

The supplied Gemini deep-research text is a source of candidate ideas, not a
verified bibliography. Its inline `[cite: n]` markers have no reference list,
so do not carry those citations or its unsupported claims into the skill.
Verify mathematical descriptions before publication. Treat 61.8/38.2 as the
definition of a proportional construction, not evidence that audiences prefer
it or understand it better.

The psychological literature does not justify presenting the golden section
as a universal aesthetic or cognitive law. [Green's review](https://journals.sagepub.com/doi/10.1068/p240937)
surveys mixed experimental findings and methodological limitations; contextual
and individual differences also matter. If the release makes a specific
empirical claim, cite the underlying study and its limits. Otherwise keep the
rationale as an explicit design judgment: an asymmetric split can give a
primary field more room when the message calls for unequal emphasis.

Do not import the report's typography scale, line-height formula, poster or
slide prescriptions, eye-movement claims, or cognitive-load claims as defaults.
Those need their own evidence and may belong to a brand or renderer. Kata owns
the information structure and reading order; Lys owns rendering behavior and
output geometry; a brand owns visual identity.

## 5. Scope and completion checks

In scope:

- A portable delivered skill with a usable decision framework and the sixth
  pattern reference.
- A worked golden-cut example in the Lys gallery and deck, including a clear
  mismatch example and an explanation of the choice.
- A repeatable evaluation corpus, CLI adapters for Claude Code, Codex CLI, and
  pi, Lys validation/rendering, and a documented results format.
- One completed evaluation report with limitations and resulting revisions
  to the framework or examples.

Out of scope unless evaluation exposes a concrete need: a general deck
narrative planner, new data-pattern families, a separate kata-lys package,
brand-specific Futurice application, and a temporal story sequence.

Completion means:

- A person or agent can follow the framework to select, adapt, or reject a
  pattern and explain the choice.
- The golden-cut reference covers fit, non-fit, and the distinction between
  spatial emphasis and quantitative encoding.
- Example builds include the new pattern and all existing integrity checks
  pass. Changed layouts receive the project's required visual review.
- The same briefs can be run through each installed supported CLI using the
  common runner, with outputs and configuration recorded for reproducibility.
- The evaluation reports choice quality, fidelity, Lys rendering, reader
  outcomes where collected, failures, ties, and sample limitations.
- The skill and its references remain self-contained when `skills/kata/` is
  copied on its own.

## 6. Issue batching guide

Deliver 0.2.0 as small GitHub issues with one owner and one reviewable result
per issue. Each issue should state its goal, file ownership, dependencies,
acceptance checks, and explicit out-of-scope items. Keep the issue titles and
acceptance criteria specific enough that an agent can finish without asking
for routine product decisions. Ready-to-file titles and complete issue bodies
are in the [0.2.0 GitHub issue packet](0.2.0-issues.md).

Use one coordinator plus at most three concurrent implementation agents.
Agents work in separate branches or worktrees, make changes only in their
assigned file areas, run the checks relevant to their issue, and open a focused
PR. The coordinator resolves integration conflicts, runs the full project
checks, and verifies the assembled release. Do not have parallel issues edit
the same source or generated files.

### Low-HITL operating rules

- Proceed independently on implementation choices already bounded by this
  plan. Ask the user only when source ambiguity changes meaning, a required
  credential or access is unavailable, a new empirical claim is proposed, or a
  scope trade-off cannot be resolved from the stated goals.
- Do not pause for routine issue wording, file organization, formatting, or
  reversible local changes. Put unresolved but non-blocking choices in the PR
  summary with a recommended default.
- Use existing authorized CLI sessions; do not request secrets in issue text or
  logs. Report a tool that is unavailable or unauthenticated and continue
  independent work.
- Reserve human review for meaning/fidelity judgments, visual communication,
  and the release decision. Automate structural, rendering, and integrity
  checks where deterministic.
- Keep evaluation data and generated artifacts separate from the examples and
  current delivered skill. Preserve failed outputs so they can inform fixes.
