## Issue 1

**Title:** `[0.2.0] Define the shared evaluation contract` — already filed as [#1](https://github.com/villetakanen/kata/issues/1)

**Body:**

## Goal
Define the stable interface for the Kata 0.2.0 Lys evaluation so the case corpus, CLI adapters, and artifact checks can be built in parallel.

**Batch:** 0  
**Owned area:** `docs/evals/PROTOCOL.md` and schema examples  
**Dependencies:** None

## Acceptance criteria
- [ ] Specify a versioned task manifest for source brief, audience question, constraints, condition, CLI/model settings, output directory, and fidelity answer key reference.
- [ ] Specify a Lys-compatible deliverable contract and required decision/rationale record.
- [ ] Specify per-run metadata, output capture, exit/failure states, and a result record that never stores credentials.
- [ ] Include one minimal example manifest and one result record.
- [ ] State how skill snapshots, prompts, and generated artifacts are identified for reproducibility.

## Out of scope
Implementing CLI adapters, creating benchmark briefs, scoring model outputs, or claiming human-comprehension results.

## Review
Keep the contract small enough for Claude Code, Codex CLI, pi, and Lys validation to share without tool-specific fields becoming mandatory.

## Issue 2

**Title:** `[0.2.0][B1] Add the pattern-choice framework and golden-cut pattern`

**Body:**

## Goal
Give people and agents a compact way to select, adapt, or reject Kata patterns, and document the golden cut as an optional asymmetric composition.

**Batch:** 1  
**Owned area:** `skills/kata/SKILL.md`, `skills/kata/references/golden-cut.md`  
**Dependencies:** Issue 1 contract

## Acceptance criteria
- [ ] Start from the audience question and identify the information relationship before choosing a pattern.
- [ ] Include adapt, split questions, and “none of these” paths; state what missing information would change a choice.
- [ ] Explain golden-cut fit and non-fit, with 61.8/38.2 as an optional starting proportion rather than a rule.
- [ ] Distinguish spatial emphasis from quantitative encoding; do not use the ratio to imply data values, winners, or aesthetic/cognitive superiority.
- [ ] Preserve the delivered skill’s portability and link the new reference from the skill’s choice table.
- [ ] Give one useful and one poor-fit example in the reference.

## Out of scope
Changing examples, building the evaluation harness, adding empirical claims without a source, or revising other pattern references.

## Review
Keep the in-task framework concise; put detailed rationale and examples in the reference.

## Issue 3

**Title:** `[0.2.0][B1] Create the evaluation briefs and fidelity answer keys`

**Body:**

## Goal
Create a small, versioned benchmark set that tests pattern choice, data fidelity, and the ability to reject a poor fit.

**Batch:** 1  
**Owned area:** `evals/cases/` and case index  
**Dependencies:** Issue 1 contract

## Acceptance criteria
- [ ] Include briefs suited to the golden cut and briefs better served by other Kata patterns.
- [ ] Include at least one case that should trigger a mismatch or a request for meaning-changing missing information.
- [ ] Include at least one untidy brief with missing values, mixed units, overlap, or uncertainty.
- [ ] Record source facts, audience question, constraints, and a fidelity answer key for each case.
- [ ] Keep cases unfamiliar and separate from the curated service-launch examples.
- [ ] Validate every case against the Issue 1 manifest contract.

## Out of scope
Running models, scoring visual attractiveness, or claiming that the cases represent all audiences or domains.

## Review
Keep answer keys factual and checkable; distinguish required facts from acceptable layout choices.

## Issue 4

**Title:** `[0.2.0][B1] Implement Claude Code, Codex, and pi evaluation adapters`

**Body:**

## Goal
Run the same evaluation task through Claude Code, Codex CLI, and pi using one shared interface.

**Batch:** 1  
**Owned area:** `evals/runner/`  
**Dependencies:** Issue 1 contract

## Acceptance criteria
- [ ] Provide adapters for `claude -p`, `codex exec`, and `pi -p`.
- [ ] Allow a selected CLI or all configured CLIs to run from the same manifest and prompt.
- [ ] Capture final response, tool/version, model/settings, timestamp, exit status, and logs in a per-run directory.
- [ ] Keep executable paths and model/settings configurable; never store credentials in manifests or logs.
- [ ] Report missing CLIs, authentication errors, and failed runs explicitly; do not silently omit them.
- [ ] Document prerequisites and one short invocation for each CLI.

## Out of scope
Creating benchmark cases, rendering Lys output, or aggregating evaluation findings.

## Review
Use isolated per-run directories and do not modify the installed skill or source examples during a run.

## Issue 10

**Title:** `[0.2.0][B4] Compare results and publish the evaluation report`

**Body:**

## Goal
Summarize the three-condition evaluation without pooling unlike tools or overstating what the sample establishes.

**Batch:** 4  
**Owned area:** `docs/evals/report.md` and aggregate results  
**Dependencies:** Issues 7–9

## Acceptance criteria
- [ ] Report choice quality, data fidelity, reasoning, Lys artifact checks, and reader-task outcomes separately.
- [ ] Separate CLI/model results; record unavailable tools, failed runs, ties, and missing reader feedback.
- [ ] Include run counts, the evaluation protocol, and sample limitations.
- [ ] Identify findings that should change the framework or examples and link to the relevant artifacts.
- [ ] Do not treat agent self-review or visual appeal as evidence of reader comprehension.

## Out of scope

## Review
Keep observed results distinct from interpretation and recommendations.
